# CVLR backend — what is left to do

A scannable index of open CVLR work, and its one list: the backend plan's §7.12 points here. Each
entry says what the thing is, why it matters, and where the argument lives. Finished work is
removed; an entry that code, tests or another document cites keeps a short note saying where the
work ended up.

The U entries were noticed while doing other work and have no section anywhere else, so this
document is their only record. The L entries are leads from the retired `certora-cvlr-kb` ledger.
The numbered entries are the plan's own open items. Upstream defects are recorded, and their routing
tracked, in [upstream-defects.md](./upstream-defects.md); entries here only point at them.

If you want somewhere to start: **U12** is a silent-staleness hole in two shipped munge kinds, and
the one with a decision in it rather than a task. **U7** is a silent-data-loss risk on the
tree-view fetch: a partial download reads as a smaller run.

---

## Unfiled — no section anywhere else

**U2. The CVLR gates do not run in CI, by choice.**
[test_cvlr_tape.py](../tests/test_cvlr_tape.py), [test_cvlr_gate.py](../tests/test_cvlr_gate.py)
and [test_cvlr_end_to_end.py](../tests/test_cvlr_end_to_end.py) are collected by the nightly
`integration-tests.yml` and skip there, silently, as a pass: that job has no platform tools, no
`run-confined` and no SolanaExamples checkout. They are developer gates, run by hand after changes to
the build, the sandbox or the submission path ([README-solana.md](../README-solana.md), *Tests*).
The toolchain is not to be added to that job. CI coverage of this path is to come from AutoProver
end-to-end scenarios instead. One wrinkle: a machine without `cargo certora-sbf` fails the
end-to-end test rather than skipping it.

**U3. Re-recording the tape has no trigger, no owner and no budget line.**
Tape lanes are keyed by `run_task` task id, so any deliberate change to the pipeline's *shape*
invalidates the tape, while a change to a prompt does not. A re-record costs roughly $213 and four
hours ([scripts/record_cvlr_tape.sh](../scripts/record_cvlr_tape.sh)). Nothing says who decides that
a re-record is due, or how you find out the tape is stale short of an hour-long failure in the
middle of a run.

**U6. The Solana property corpus's inputs live in a repository that is being retired.**
Where each piece of CVLR knowledge comes from is settled, and all of it is built here. The manual
is built by [gen_docs.sh](../scripts/gen_docs.sh) and ingested into `cvlr_kb` by
`ragbuild --corpus cvlr`. The API reference is generated by `composer.scripts.cvlr_api_docs` into
its own corpus, `cvlr_api_kb` ([cvlr-api-docs-plan.md](./cvlr-api-docs-plan.md)). Practice
knowledge is not a corpus: it is the hand-written CVLR bundle and recipes
([cvlr-knowledge-plan.md](./cvlr-knowledge-plan.md) Part I). Nothing from `certora-cvlr-kb` reaches
a corpus here, and that repository is being retired.

What is left is the one thing that still depends on it. The Solana property corpus (the knowledge
plan's Part II, in certorag) would reuse its project inventory, `locate.py` and the deterministic
parsers in `extract.py`. They have to move before the repository goes, and certorag, their only
remaining consumer, is the natural home (§11–§12.7 there).

**U7. A partial tree-view fetch reports itself as complete.**
POU's `fetch_job_treeview` downloads each output file in a thread pool and *swallows* per-file
failures — it logs `Warning: Failed to fetch <name>` and then writes the completion marker anyway.
A dropped connection during the fetch raises, and `fetch_sources_and_treeview_files` in
[cloud.py](../composer/prover/cloud.py) retries it. The same blip during the tree-view half raises
nothing, and leaves a results directory missing rules, which
[read_and_format_run_result](../composer/prover/results.py) parses as a smaller run. The retry
cannot help: it fires on a raise. Nothing downstream can tell that from a job that genuinely had fewer rules. This is
upstream code (`certora-prover-cli`), so the work is to confirm the reading against the installed
version, decide
whether a completeness check belongs on our side, and route it with the rest of
[upstream-defects.md](./upstream-defects.md).

**~~U9. Should `optimistic_loop` be the default, as it is on the CVL side?~~** — **resolved: no;
it is an escape hatch.** `adjust_prover_config` takes a `SetOptimisticLoop` edit with its reason
(`OptimisticLoop` in [conf.py](../composer/spec/cvlr/conf.py)), and the bundle's loop ladder has it
as the fourth rung: constrain the loop, munge it, raise `loop_iter`, and only then assume it
terminates. The tool's charter says two of its settings are sound and this one is not. The default
stays off. The EVM side sets it on every run ([source/prover.py](../composer/spec/source/prover.py)).

The measurement that decided it (2026-09-21): one rule, the real vault `deposit` handler,
`balance_post == balance_pre + amount` over `NativeInt`, submitted against the delivered `Deposits`
harness with only the conf changed
([vault-deposits.pin.json](../tests/data/pins/vault-deposits.pin.json)):

| conf | verdict |
|---|---|
| `loop_iter 2`, `optimistic_loop` off | VIOLATED — *Unwinding condition in a loop* |
| `loop_iter 8`, `optimistic_loop` off | VIOLATED — identical trace; the Prover's advice just says "higher than 8" |
| `loop_iter 2`, `optimistic_loop` **on** | **VERIFIED** |
| the same, with `cvlr_satisfy!(true)` in place of the assertion | VERIFIED — so the path is live and the proof above is not vacuous |

The loop is `system_instruction::transfer`'s own bincode/`Vec` construction, inlined into the
handler where no summary or munge can name it. It terminates in reality, so assuming it does assumes
something true; without the assumption the handler cannot be verified at all. The flag's defect is
that it is **per submission, not per loop**: it also assumes away the program's own loops, which is
the risk `conf.py`'s rationale describes.

So the remedy differs by case. For a loop the property is about (a list scan, an accumulation),
`mock_fn` on its accessors is the remedy the bundle teaches, and it keeps the assumption local: the
hand-written stake-pool verification mocks `BigVec::find` this way and sets `optimistic_loop` false
everywhere. For a loop no mock can reach, like the vault's, the flag is the only remedy. On a re-run
with the rung available, the author skipped the property rather than climb to it, so the rung's
framing weighs on whether it is used.

**U12. A munge that points at an author-written stand-in can have a justification that is no longer
true, and nothing detects it.**
Found by the harness judge on the U11 run, blocking a draft: *"The `invoke` munge record materially
misdescribes the stand-in it redirects to. … The redirect points at whatever the harness currently
defines, so the record is stale."* The author had rewritten the stand-in twice after the munge was
recorded and approved; read against the rules shipped beside it, the stale `why` would have made one
assertion false and another double-count. The same judge found a second stale record in the same
draft.

`ModuleRedirect` and `FunctionExtraction` are immune by construction — their `edit_id` digests the
code they carry, so re-authoring it is a different edit that inherits neither the review nor the
prover stamp. `ImportSwap` and `MockFn` carry a *path* into the author's own harness, which the
author may rewrite freely. **`mock_fn` has shipped with this since the beginning**, so this is not a
regression from the new kind; it is a property of the design that the new kind made visible.

It is a decision rather than a patch, and the options are not equivalent. Digesting the stand-in's
source into `edit_id` invalidates a review on every unrelated edit to that harness file. Digesting
only the named item needs a resolver `munge.py` does not have and would tie it to Rust parsing it has
so far avoided. Prompting the author to `amend_munge` after rewriting a stand-in is what already
happened — one judge round late, and only because that judge chose to reconcile the record against
the artifact. A fourth option is to make the *report* state that a stand-in's description is the
author's claim rather than a checked fact, which is cheap and honest and fixes nothing.
[who-edits-the-program.md](./who-edits-the-program.md) §13.4 has the argument.

**U14. A stand-in munge's gate says something weaker than what it needs.**
The munge reviewer's non-blocking nit on the U11 run, and it is right: a `swap_import`'s aliased
`use` is gated on the requesting unit's feature alone, while the `mod certora` declaration holding
the stand-in is gated on `certora`, so `--features unit_x` without `certora` would compile a `use`
of a module that is not there. It cannot happen today — `declare_unit_features` makes every unit
feature empty and the build always passes `--features certora,unit_x` together — and `mock_fn`'s
`stand_in` has exactly the same shape, so this is one decision for both kinds rather than a patch to
the new one. Either gate on both features, or write down that the pairing is guaranteed by
`declare_unit_features` and the build invocation, so the next person to add a way of building does
not quietly break it. Worth an hour, and cheaper before something else depends on it.

**U13. The vault scenario's `withdraw` has an unexercised aliasing case, and the harness judge found
it before we did.**
Not a defect in the backend — a gap in the scenario and in what a rule about it covers. `withdraw`'s
`fee_collector` is an `UncheckedAccount` with no constraint beyond `mut`, so passing the vault itself
as the collector is a legal call and the classic aliasing shape a solvency invariant is asked about.
The U11 run's rule assumed it away (`accts[0].key != accts[2].key`) and the judge flagged the
exclusion as unexplained, noting it had checked the arithmetic and the invariant does still hold
(`cushion' = cushion + fee`). The open question is whether `cvlr_deserialize_nondet_accounts` can
model aliasing at all — it gives each slot its own lamport cell, so two equal keys may not share a
balance — which decides whether the assumption is a narrowing to disclose or a modelling limit to
record. Cheap to settle, and it generalizes: any rule over two accounts of one type has this
question.

**U16. Timeout-cracker support, in place of the nonlinear solver portfolio.**
*The portfolio was dropped on eric/cvlr-preflight on 2026-09-22 and back-ported.*
`adjust_prover_config` has lost `SetNonlinearSolverPortfolio`, so the author has no solver-side
remedy for a rule that halts on the global timeout. The candidate replacement is the
Prover's own `-timeoutCracker true`, which the CVL codegen tool already passes
([prover.py](../composer/tools/prover.py)). It is not a flag that composes with others: on entry it
resets the backend strategy, `-smt_useLIA`/`-smt_useNIA`, `-solvers`, the solver timeout and the
splitting options, then runs its own recipe — a z3 first pass split to depth 5 under a hard-coded
3600s budget, then five configurations per unsolved split, two of which are z3 and cvc5
random-seed races much like the portfolio was (`verifier/TimeoutCracker.kt`). So it is a choice
between recipes, and belongs in `ProverSettings` as one variant of a solver strategy rather than as
a boolean beside another. Two things are unestablished: that a Solana rule reaches it (it is invoked
from `TACVerifier`, which Solana rules share, but no Solana run has set it), and whether it does as
well as the portfolio did on the P8 rig — 109.3 minutes with the hardest rule unresolved without
the portfolio, 4.6 minutes with every rule verified with it
([upstream-defects.md](./upstream-defects.md) P8, postscript). That rig is the measurement to
repeat.

**U17. A run that withheld a CVLR specialization does not say so in the report.**
`ChainReference.withholding` lets a run keep a specialization out of the target, for the case where
the target *is* the program that specialization models — verifying the stake program with
`cvlr-solana-stake` in scope hands the author a model of the instructions it was asked to specify
([stake-benchmark.md](./stake-benchmark.md)). The narrowing is visible while the run happens:
`CvlrPreflight.describe()` logs it, and the withheld crate shows up in the gap list as "not a
dependency of this project". It is not in the artifact a reader keeps, so a benchmark number
published from such a run does not state the reference set that produced it, and a second run under
the default set is not obviously a different experiment.

**The nearest precedent was deliberately dropped, and this should not quietly undo it.** The
`build_environment` field — same shape, recording whether a run's builds were confined — was removed
before review on the grounds that *nothing reads it* (cvlr-landing-plan.md, "Dropped: reporting
whether the builds were confined"). That argument holds here too for as long as the withholding flag
is used by one benchmark on one branch. What would change it is a published comparison: a number
someone outside this repository is asked to trust needs its conditions attached, and that is a
reader the confinement field never had. So this is a workitem conditional on the benchmark actually
publishing, not a gap to close on general principle — and whoever picks it up should reread that
dropped section first rather than treating the absence as an oversight.

**U18. A run's spend is logged per call and surfaced nowhere.**
`composer.diagnostics.usage_callback` writes a DEBUG line per LLM call into
`.certora_internal/autoProve/<run>.log` carrying model, task, cost centre, thread, node and the full
token split (`in`/`out`/`cache_read`/`cache_write`). Everything needed to price a run is therefore on
disk while it happens — `composer/diagnostics/cost_callback.py` holds the arithmetic, and
`total_input_tokens` *includes* the cache figures, so a naive sum over `in` overstates a cached run
by roughly 4x. What is missing is any path from there to someone watching. A `--budget-total` run
prints no running total, the events stream carries no usage fields, and the only way to answer "how
much has this cost so far" is to grep the DEBUG log and reimplement the pricing. Measured on the
stake benchmark: 429 calls, 784 fresh input tokens against 25M cache reads, ~$57.

The fix is small and there are two halves worth separating: a periodic line on the run's own output
(the budget ledger already has the numbers), and a reusable reader so that grepping DEBUG logs is not
how anyone answers this twice. Distinct from [[U17]], which is about the *reference set* a run used
rather than what it spent.

**U20. The CVL author's draft cache has the hole the CVLR one just had fixed.**
`cache_put` refuses writes made under budget pressure, which is right for a result and backwards
for a resume buffer: the run whose draft most needs carrying forward is the one the budget cut, and
that is exactly when the guard fires. `CacheKey(..., survives_budget_pressure=True)` marks the
exception and `composer/spec/cvlr/author.py` uses it. `cvl_generation.run_cvl_generator` caches its
draft the same way and does not, so an EVM run cut by the budget still re-authors from nothing.

It is one argument to add, but **do not add it on its own** — see [[U22]]. The opt-in is what lets a
curtailed run overwrite a better cached draft, and CVL is currently shielded from that only by
having the hole. The guard against regressing and the opt-in belong in the same change.

**~~U21. A run that delivered partials under budget pressure reports itself as a total failure.~~**
— **fixed (3dae956b).** `CorePipelineResult.all_failed` counts a curtailed partial as output
(`n_partial`), and the consoles print `RUN CURTAILED` and exit 0. **Still open:** the three console
summaries (`console_solana`, `console_foundry`, `console_autoprove`) are ~42 near-identical lines
each and should be folded into one, carrying CVLR's unwrapping of a `Curtailed` to name the partial
it wrote; the other two do not name it. Dispatch under budget pressure stays as it is: a unit started
after the pool is spent costs seconds and records its properties as skipped.

**U22. The draft carry-forward can overwrite a better draft with a worse one.** *(CVLR side fixed; CVL side open.)*
`_remember_attempt` caches whatever `curr_spec` holds when the unit unwinds, with no comparison
against what is already there. On 2026-09-24 the stake run finished with 1,609 lines and 12 rules in
the cache, over the 6,176 lines seeded into it that morning.

**This and [[U20]] are one design question, and fixing either alone is wrong.** `cache_put` drops
writes made under budget pressure unless the key opts out. CVL's key does not opt out, CVLR's now
does, and the two failure modes are complementary:

| | run cut by the budget | run that ends normally |
|---|---|---|
| CVL (no opt-in) | writes nothing — keeps the older draft, loses its own | overwrites unconditionally |
| CVLR (opted in) | overwrites — can regress | overwrites unconditionally |

Neither is right. Without the opt-in a budget-cut unit caches nothing, which is the bug the opt-in
was added to fix — the carry-forward silently no-opping in exactly the case it exists for. With it,
a run that achieves less than its predecessor replaces the predecessor's work.

**CVLR now takes the shortest route that makes the opt-in safe:** a unit whose state carries
`budget_curtailed` may *fill* an empty slot but never *replace* an occupied one. Seeding an empty
slot is the case the cache exists for and cannot regress anything; replacing a fuller draft with a
post-wrap-up remnant is the only loss actually observed. A unit that finished on its own terms still
overwrites unconditionally, which is CVL's behaviour and the right one — a smaller *considered*
draft is the better thing to resume from. The per-unit `budget_curtailed` flag is the test rather
than `budget_pressure()`, because the run pool is shared and near the end of a run every unit sees
pressure whether or not it was cut.

CVL should get the opt-in **and** this guard together, not the opt-in on its own.

`ap-trail recover-drafts --draft largest` repairs the cache from the checkpoints after the fact,
which is a workaround and not a reason to leave this.

**Two places the CVLR version is ahead of CVL's, worth carrying back:**

* `LastCvlrAttempt` carries the `munges` the draft was written against (as `describe()` strings, not
  values — see the class docstring for why). CVL's `_LastAttemptCache` holds only `cvl`.
* `_remember_attempt` is wrapped in try/except and logs. CVL's `finally` is unguarded, so an
  `aget_state` that throws replaces whatever exception was already unwinding — including the
  `BudgetExceeded` that caused the unwind, turning a budget stop into an unrelated traceback.

**U23. The byte-decomposition idiom for `Pubkey` is unsound under the Prover.**
A harness that decomposes a `Pubkey` into four `u64` words via `to_bytes()` + `u64::from_le_bytes`
does not round-trip: `words_pk(pk_words(&p)) != p` for a single nondet key
(`rule_diag_pubkey_eq_stable`, 2026-09-24). The judge's diagnosis is that the prover cannot relate
bytes written by `to_le_bytes` to bytes read back by `from_le_bytes` through an intermediate
`[u8; 32]`, so the byte-level and aggregate views of the key are unrelated objects to the analysis.
Any comparison built on the word view is then four comparisons over unconstrained values.

Two consequences. The authoring guidance should steer away from the idiom — this is a trap an agent
will otherwise re-derive, as one did here. And the long-standing suspicion that native `Pubkey`
equality on SBF (`sol_memcmp_`) is unconstrained is **not supported**: the same rule checked it and
it was stable and repeatable. The remaining vacuity cluster needs a different explanation; the
`rule_probe_hashset_*` / `rule_diag_signer_set*` rules coming back *violated on a prover-generated
assertion* are the next lead, as is `rule_diag_signer_set_membership` pinning the longest job of both
runs.

**U24. The Rust build sandboxing scheme has never had a full security audit.**
Every CVLR build compiles and runs native code that neither we nor the user wrote: the analyzed
program's `build.rs` and proc-macros, and the LLM's edited source. The only thing between that code
and AutoProver's secrets, network and filesystem is the Landlock + seccomp confinement
([command-sandbox.md](./command-sandbox.md), [composer/sandbox/](../composer/sandbox/),
[rust/run-confined/](../rust/run-confined/)). What checks it today is the escape suite we wrote
ourselves ([test_sandbox_escape.py](../tests/test_sandbox_escape.py)), and the gaps found so far were
found by accident: the x32-ABI seccomp bypass, and the shared `CARGO_HOME` that let one run poison
the next. Wants a dedicated adversarial review of the whole scheme. That covers the threat model in
§2, the seccomp deny-list (residual risk compared with a default-deny allowlist), Landlock ABI
fallback on the kernels we deploy to, and same-uid recovery of secrets through `/proc` or `ptrace`.
It also covers every read-only and writable grant in `rust_build_policy` and the CVLR recipes, the
unsandboxed warm `cargo fetch`, and the environment allowlist. The open questions in
command-sandbox.md §11 are where it starts, not its scope.


**U25. Ship blocker: the Solana conf pins `prover_version: master`.**
`BASE_CONF` ([conf.py](../composer/spec/cvlr/conf.py)) turns on `-solanaTACSoundSignedMath`. Without
it, a `u64` compared against a constant at or above `2^63` is modelled as a negative comparison, so
a program's `== u64::MAX` branches are never taken ([upstream-defects.md](./upstream-defects.md)
P11). The fixes that let the flag coexist with `-solanaTACMathInt` (P8) are on the Prover's master
branch but not all released, so the conf also names `prover_version: master`. That is right for
development and wrong for a shipped product. Remove `prover_version` once those fixes are in a
release, and rerun the CVLR gate against the released Prover first, since P8's two-hour timeouts are
what the release has to have fixed.

**U40. Long Prover jobs set the pace of a run.** On the benchmark run, Prover time was 24 hours
across 75 calls. Jobs of 20 to 30 minutes were common, 6 halted at the ceiling, and units spent most
of their wall clock waiting. Find out what the long jobs are before moving `global_timeout`: which
rules, and whether they are the wide-integer arithmetic, the loops, or the translation. A halted job's
finished verdicts are not returned (U32), so each halt also discards the rules that did finish. That
makes U32 worth doing for the Solana backend on its own. (Built 2026-11-02; see U32.)

*Measured 2026-10-30: it is wide-integer division.* The data comes from 7 of run 2b's job output
archives (`Reports/treeView`: the per-rule `rule_live_statistics_*.json` and the final
`treeViewStatus_*.json`). The median job ran 26 minutes, and every job carried some rules to the
ceiling. All rules were in the solving phase, not translation.

* **Wide division.** Of the 18 rules that did not finish (timed out, still running at the halt, or
  the solver not answering at the hard stop), 10 have `div_rem_u256_u128` / `div_rem_256by128` as
  45 to 67% of their branching, at path counts of 2^109 to 2^221. That is the 256-by-128-bit
  division under the program's `Fraction` fixed-point type. The six slowest rules that did finish,
  at 12 to 22 minutes each, have the same profile.
* **Nonlinear arithmetic.** Five of the other eight have nonlinear arithmetic, up to 40 operations
  of degree 8.
* **Loops.** Two are loop-heavy, with 28 loops.
* **Unclear.** One shows no hotspot at all.

Raising `global_timeout` would buy little on rules at 2^170 paths.

*Tried 2026-10-30: characterizing the division makes it worse.* The test reused the borrowing unit
of run 2b: its 14 rules and settings, and the job's own sources from its output archive. The unit's
author had already replaced `uint`'s types with an exact loop-free stand-in. In the variant, that
stand-in's `div_rem_256by128` became a pair of nondet `u128`s constrained by `r < d` and
`q*d + r == n`, which is exact under the function's `n_hi < d` precondition. The variant was
submitted next to two baselines, the job's own binary and a local rebuild of the same sources. The
two baselines agreed to within noise. In the variant:

* Path counts fell sharply (2^114 to 2^67, 2^159 to 2^88), and division's share of branching fell
  from 43-65% to 6-16%.
* But the expensive rules got slower. All 4 that had verified in 15 to 21 minutes timed out. The 6
  that still finished are the cheap ones, under 4 minutes, and only one of them reaches the
  division. That one went from about 3.5 to 2.5 minutes.

Path count is not what the solver pays for here. A free quotient multiplied by a symbolic divisor
is a harder query than the long division's branches. So "make the division cheaper" is the wrong
lever. The candidate left is a *narrower fixed-point type* under the verification feature: a
64-bit `Fraction` in place of the 128-bit one, with no 256-bit intermediate at all. It is not
exact. It changes rounding, so it is a modeling decision that every affected verdict must state,
and it cannot support a property about rounding or precision. It would be a new editor kind, with
that caveat in its `why_sound`. Measure it the same way before building it.

*Tried 2026-10-30: the narrow type is fast where it holds, but it is not a drop-in edit.* The test
swapped in a 64-bit `Fraction` (14 fractional bits, in place of 60) under the unit's feature. To
compile against this version of the program, it needed eight small coordinated edits: interest
accrual and one ceiling conversion redone in `u128`, a missing method, two literals. Then:

* **Unchanged harness.** The whole job took 10 minutes instead of 25, but 8 of the 14 rules came
  back sanity-failed, which is vacuous. The harness encodes the 60-bit scale (`ONE_SF = 1 << 60`,
  and a deposit near 2^80), the narrow type assumes every encoding fits in 64 bits, and the two
  contradict each other. Stored `_sf` fields carry the program's encoding, so narrowing re-reads
  every stored value.
* **Harness constants rescaled to 14 bits.** Three more rules came back, each passing its vacuity
  check. One went from 17 minutes to 3.5, and two that had timed out took 8 seconds each (on path
  counts small enough to deserve a look before believing them). One cheap rule went from 3.5
  minutes to 16 seconds. The 5 rules over the borrow path stayed vacuous, so the program still
  encodes the 60-bit scale somewhere on that path.

So the narrow type is a real lever, but only as a decision made at the start of a unit. The
program's fixed-point encoding, the harness's constants and every stored field have to agree on
it. It is not something an author can apply to rules already written, and it is not a cheap
editor kind. The cheaper wins for U40 are U32 (a halted job keeps the verdicts that finished; here
the halt would have kept 9 or 10 of 14) and smaller jobs, so that one slow rule does not hold the
ceiling for the rest.

*Prover flags are not the lever either (2026-10-30).* The same binary and rules were rerun under
two other sets of Prover args:

* Ours without `-unsatCoresForAllAsserts`.
* A hand-tuned set: CFG-diamond removal, the optimistic join/overlap/memcpy/memcmp/memmove
  options, aggressive global detection, and 6 slicer iterations.

Neither changed what finishes. Each job still ran to the 25-minute ceiling. Without unsat cores,
the expensive rules took the same time. The hand-tuned set made them 10 to 20% slower: 1169 s
against 966 to 987 s, and 999 s against 880 to 888 s. It finished one more rule than the run 2b
binary did, but the second baseline did too. One rule flips between verifying in about 21 minutes
and timing out across identical submissions, so a difference of one rule is noise. Several of the
optimistic options also carry memory-model assumptions that would have to be stated beside the
verdicts. So the speed of a hand-written spec for this kind of program comes from how it is
designed: the fixed-point type, stand-ins for whole subcomputations, and jobs of one to three
rules. It does not come from flags.

in the lending benchmark's liquidation unit compares ratios that the program computes with 25
fixed-point divisions, each a 256-bit long division (U44). A stand-in (U43) cannot replace those

**U47. The Solana AutoProver has no evaluate mode (deferred).** Evaluate (#282, not yet merged into
`feature/solana`) writes no specs. It runs the specs and confs already in the repository and reports

needs its own implementation. It has to find a project's existing CVLR rules and the confs that
select them, run them through the CVLR verify path, and judge per property which rules cover it.
The API and dashboard would need the same per-kind lifting as U46, and the dashboard's flat
evaluate price. Left until after U46.

**~~U48. A generic impl's account validation stayed external.~~** — **fixed (2026-11-04; on the
third liquidation run two `try_accounts` rules verified the owner and market bindings).** The Anchor inlining layer inlines `<.. as anchor_lang::Accounts<..>>::try_accounts`

**U49. The Solana launch form has no Expert Settings panel.** The Solidity AutoProver form
(zeus-saas `auto-prover-sections.tsx`) shows only the essentials by default and keeps the rest
behind an `ExpertSettingsToggle`: the contract picker, the run mode, *Use repo memory* and the
design and threat-model documents. The Solana form (`auto-prover-solana-sections.tsx`) has no such
panel. Its program picker, run-mode picker and design-document picker are always shown, and it
offers no repo memory and no threat model. The Solana form should get the same panel and the same
default view, so that the two apps look and behave alike. The panel is also where any future Solana
settings would go. Moving the run mode behind it should keep Prioritized as the default, as the
Solidity form does.

**U50. The dashboard does not show a narrowed property's scope.** A prioritized CVLR run checks a
property that names other components' entry points only at its own component's
(`prioritize.scope_to_unit`, `ScopedPropertyFormulation`). The report records each narrowing in
`run_scoped` (schema 3.8): the component, the title, `checked_at` and `excluded`. zeus-saas does
not read that field, so a narrowed property's verdicts look like any other property's, and a
balance floor verified at `withdraw` alone reads as the floor holding across the program. The
report view should mark each narrowed property, list the entry points it was checked at and the
ones it was not, and say that the exclusion is the run's scope rather than a finding about the
code. The run overview could say how many pursued properties were narrowed. This should ship with,
or before, the first prioritized Solana runs that users see.

U51 to U55 come from a prioritized benchmark run on a Solana lending program's liquidity layer
(dev cloud, 2026-11-05): 53 rules, 20 Prover jobs, 6 of them halted. Each is general.

**U51. A finding's severity does not distinguish code-reachable from deployed.** U36 asks whether
the program can reach a counterexample's pre-state. It does not ask whether the deployment does.
On the benchmark, a claimed finding needed a mode the program allows any configured protocol to
use, but the protocol's published verification work says only one program uses it, and in a way
that never produces the state. The author called it high, and it had no way to know otherwise:
nothing it reads describes the deployed configuration. The report should give a finding's
reachability as one of: from any state the handlers allow, only under configuration an
administrator would have to choose, or not shown. The severity should follow from that, not from
the impact alone. The design document is where a user could state the deployment's configuration
(which protocols use which modes, which admin settings are live). The Solana form takes no threat
model yet (U49), and that document is the natural home for it.

**U52. A rule that pins a scale factor at its initial value hides unit bugs.** Every accrual rule
on the benchmark assumed both exchange prices were at their initial value of 1.0 ("prices at their
initial value", bounded for tractability). At 1.0, a raw amount and its face value are equal. So the
run could not see a defect that mixes the two, and one was in the benchmarked code: the supply ratio
compared raw with-interest supply against face-value interest-free supply, published as M-04 in
Certora's second Jupiter Lend report (*Formal Verification, Jupiter Lend, January–March 2026*,
`lend-certora-fv-2.pdf` in `jup-ag/docs/static/files/audits`) and fixed upstream after that
release. The author's operate rules pinned prices at 1.25 and 1.5, but ran in the same second, so
they never reached the accrual. Guidance for the author and the judge: a domain pin that makes two
quantities coincide (a price at its precision, a ratio at 1, two decimals equal) is a restriction
to lift, not a domain. At least one rule over the code that converts between them should run with
the factor away from its identity value. The judge's domain check (item 2) could name the pattern.

**U53. Repeated halts on the same rules do not change the author's approach.** The benchmark's
author sent the same timing-out rules back five times in a row; every one of those jobs halted at
the 25-minute limit. U32 returned each halted job's finished verdicts, and the Prover's note said
to simplify or split the rules that timed out. The author kept editing them in place for about
2.5 hours, without skipping, splitting or isolating them, and never tried `give_up`. It recovered
only when it deleted them (U54). klend run 4 showed the same pattern. After a second consecutive
halt in which the same rules have no verdict, `verify_rules` should refuse to resubmit them alongside
the rest. The author would then have to isolate them in their own job (U34 would make that a selection),
narrow them, or account for them. The refusal message is a prompt, so it should name the rules and
the three options.

**U54. A rule dropped after it reached the Prover leaves no trace in the report.** Skips are
recorded per property. A rule is only checked for belonging to some property. On the benchmark,
the author ended the halts of U53 by deleting the three rules for an `operate` that both
withdraws and borrows, including the path that merges the two payouts into one transfer. Their
properties still mapped to other rules, so `result` accepted the unit, the report lists nothing as
skipped, and the component reads as complete with one code path unverified. The run knows every
rule that ever received a verdict (the stamps' history). A rule in that set that is missing from the
final spec, above all one whose last verdict was TIMEOUT, should either be accounted for by the
author before `result` (why it was dropped, and what still covers its path) or appear in the report
as dropped with its last verdict. The judge should see the list.

**U55. A preflight refusal does not reach the cloud UI.** The benchmark's first run stopped in
preflight about 40 seconds in, on a scaffold `Blocked` entry (the anchor-lang double resolution, fixed in
31c81906). The UI showed the run as failed with no reason. The only record was a `PreflightFailed`
traceback in the executor's CloudWatch log, which a user cannot read. `PreflightFailed` already
carries a reason meant for the project's owner, with each blocked item's problem and resolution.
The Solana executor (AIAutoProver `s3_autoprove_solana`) should write it where the workflow's
status is shown, the same way a run's report is. This is the preflight counterpart of the deferred
fix for a Prover job's FAILED reason.

**U56. An invariant one unit proves cannot be assumed by another.** Each unit's harness module is
declared behind its own cargo feature (`harness.declare_modules`), so units build in isolation and
one unit's broken draft cannot break a sibling's build. The same isolation keeps every predicate in
its unit. A component cannot call the protocol unit's invariant, and nothing tells its author which
invariants have been proved. Hoisting (`composer/spec/hoist.py`) moves a property several
components state into the shared "Protocol invariants" unit and dispatches that unit first. But the
hoisted claims reach only the report (`HoistedClaim`), and dispatching first is scheduling, not a
dependency. So a component that needs solvency to exclude an unproduced pre-state (U36) proves it
again, or falls back to U37's second and third remedies, a justification rule or a bare
`cvlr_assume!`, for a fact another unit may already have proved.

The CVL skill has the shape that fixes it: `invariants.spec` is proved before any component,
changed only at a barrier, and imported by every spec. For CVLR:

- An `invariants` module under `specs/`, gated on `certora` rather than a unit feature, so every
  unit's build compiles it. Its invariants are proved as U37 describes, with the writers listed
  across the whole program, not one component, and a gate of every base case and step VERIFIED,
  none expected-to-fail.
- The unit that writes it runs to that gate before the others start. That makes the staged
  formalizer order a dependency, not a queue position. A later unit's request for a new invariant
  goes through the staging writer, then the gate runs again before any unit uses it.
- Each later unit's prompt lists the proved predicates and the step rules behind each. The judge
  rejects a `cvlr_assume!` of a shared predicate that did not prove.
- The shared module owns the trait impls its invariants need. Units are never compiled together
  today, so two can each write `impl Nondet for Pool`. With a module every unit compiles, a unit
  that repeats one of its impls fails with `E0119`.

U37's recipe has not yet been exercised by a run, so this is worth building after the first run
that proves an invariant, not before. `docs/cvlr-skill-plan.md` designs the same module for the
Solana skill, where the orchestrator plays the staging writer.

**U57. A cloud job that never leaves the queue is reported as a failed job.** `cloud_results` polls
a job for `runtime_bound + 5 min` (`prover/core.py`, `poll_timeout`), counted from submission, so
queue time uses up the budget meant for the Prover's runtime. On the 2026-11-06 stake run
(`70635f3a`) an EC2 throttling incident in us-west-2 kept job `01413cbd` `RUNNABLE` for over 25
minutes. The poll timed out, `poll_job`'s `TimeoutError` became `CloudJobError(JobStatus.UNKNOWN)`,
and the author was told "Prover cloud job did not produce results (status UNKNOWN). The job and its
failure output are at …" (`cloud_job_failure_message`). Nothing says the job never started, so the
author cannot tell an infrastructure delay from a halt on its own rules. It resubmitted, but it
could as well have cut or weakened rules that were never run. The abandoned job is not cancelled,
so it runs for nothing once capacity returns.

The fix has three parts, all in shared code (`prover/cloud.py`, `prover/core.py`), so CVL runs get
it too:

- Count the runtime bound from the first `RUNNING` status. Bound queue time separately and
  generously, or not at all.
- Make "never started" an outcome of its own rather than `UNKNOWN`. The text should say how long the
  job waited, that this is an infrastructure delay and not a verdict, and that the same draft should
  be resubmitted unchanged.
- Cancel a job the poll gives up on, if the cloud API allows it.

**U58. Programs on a zero-dependency framework (Pinocchio, jiminy) are refused in preflight.** A
platform generation is recognised by a witness crate the package links, `solana-program` or
`solana-account-info` ([reference.py](../composer/spec/cvlr/reference.py)). A program written on
Pinocchio or jiminy links neither. Each framework brings its own entrypoint, account type and
syscall bindings, and the `solana-*` crates in such a workspace are typically dev-dependencies for
Mollusk tests. `select_package` therefore refuses the package: "on no Solana platform generation
this build supports. It builds none of the platform crates that identify one." A dev-cloud run on
2026-11-09 against a jiminy program stopped there, before any LLM call. The refusal is right for
this build. Every reference set pins `cvlr-solana`, whose account helpers produce
`solana-account-info`'s `AccountInfo`, and the scaffold, the prompts and the examples all assume
that type. Nothing in this repo mentions either framework outside one benchmark note. New programs
that care about compute units increasingly use these frameworks, so expect this refusal more often.

Practitioners already verify Pinocchio code. The P-Token specs depend on `cvlr` alone, not
`cvlr-solana`. They build nondet accounts themselves, transmuting a
`CVT_nondet_solana_account_space` buffer into Pinocchio's `AccountInfo` (`cvlr_new_account_info`,
`cvlr_deserialize_nondet_accounts_unchecked`). That works because Pinocchio's `AccountInfo` is a
pointer into the runtime's serialized account. Whether jiminy's account type allows the same
construction is unchecked. Support needs:

- A platform generation per framework, with its witness (`pinocchio`, `jiminy-entrypoint`) and a
  reference set of `cvlr` plus a shim for nondet accounts, instruction data and sysvars. Where the
  shim lives is open: a `cvlr-solana` feature is the better home if more than one framework or
  project needs it, the scaffold otherwise.
- Prompts and examples written against the framework's account type rather than `AccountInfo`.
- Before either: a refusal that names the framework. When the package links a known one, say that
  Pinocchio or jiminy programs are not supported yet. Do not list generations the owner has no way
  to move to. This is cheap, and it reaches users only once U55 lands.

modelled as writing *nothing* except `r0` and the cells its summary names
(`sbf/tac/TACDefaultSummarizer.kt`: `summarizeCall` havocs those and returns; a `num` on non-stack
memory does not even write memory). Every other write the real function makes is dropped. cvlr says
the same of `memhavoc_c` ("the bytes keep whatever the Prover already knew about them"). So a
summary's effects are an **under-approximation**. It fakes a return value; it does not say "anything
could happen". The unsound case is a dropped write to memory that already held a value. The rule then
sees the old value, so an invariant over that state passes trivially. Six places in AutoProver
describe a summary the other way, as "anything could happen": `cvlr_property_generation_prompt.j2:105`,
`cvlr_property_judge_system_prompt.j2:40`, `verify.py:715`, `state.py:283`, and `tuning.py:13` and

function that *writes* state a rule asserts over, not only one whose result it reads).

## Blocked on upstream

**1. A summarized CPI may havoc the caller's deserialized `Account<T>`.**
Once the most serious constraint on this backend, now unconfirmed. A direct probe on 2026-09-29 did
not reproduce it: across a summarized `invoke` the deserialized account is untouched, and the CPI's
own writes are dropped instead (L1). The handler form it was first observed in could not be

removes the dependency for any handler whose CPI goes through a `use`. See
[upstream-defects.md](./upstream-defects.md) P6.

**2. An acceptance property cannot be stated at all.**
Found by a run — by a run, not by reasoning. A rule that binds a
handler's `Result` and asserts `is_ok()` comes back vacuous, while six rules with an identical

result assumes success, which is what an acceptance property is trying to establish. It takes with it
every property enforced by Anchor's generated account validation, whose outcome is unobservable in
the same way and demonstrably unstable across builds. The suspected mechanism is the niche-encoded
`Result<_, anchor_lang::error::Error>` with the Certora fork's unboxed `Error` — the same fork item 1
of *Blocked on upstream* and P1 say we depend on. See [upstream-defects.md](./upstream-defects.md)
P9.

**3. Most of the upstream defects are filed nowhere.**
Which defects are filed, and which are fixed, is kept in one place: the introduction and table of
[upstream-defects.md](./upstream-defects.md). Routing the rest is the open work. Until each is
routed, the next engagement rediscovers it.

**11. The disposability invariant end to end.** The work directory is a temporary directory created
