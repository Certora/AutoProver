Harness for the Admin Setup component of the `Token` contract. Five rules over four properties, all driving the contract's own entry points (`crate::Token::initialize`, `crate::Token::mint`, `crate::Token::balance`). The harness defines only three observation helpers — `admin_opt` / `admin_is_set` read the persistent `"ADMIN"` entry with exactly the key spelling and durability `mint` uses (`e.storage().persistent().get/has(&"ADMIN")`), and `addr_id` extracts an `Address`'s Val payload for logging. No contract logic is reimplemented.

Modelling notes and assumptions:
* Pre-state is arbitrary contract storage; each rule restricts it only with `admin_is_set` / `!admin_is_set`, matching the pre-condition each property names. The stored admin is *read out* of storage, never written in, so the rules quantify over every installed admin.
* Authorization is modelled by `cvlr_soroban::is_auth`, read into a local *before* the call and *asserted* afterwards (record–call–assert), so each rule constrains exactly the successful invocations. No rule assumes auth for a privileged address, and no rule uses the `assume-violation; assert!(false)` spelling (the conf's `rule_sanity` would report it vacuous).
* `cvlr_assume!(bal.checked_add(amount).is_some())` in rules 1 and 5 scopes those rules to non-overflowing mints; the release profile sets `overflow-checks = true`, so an overflowing `receive_balance` traps and the host rolls the whole invocation back.
* `rule_sanity` must stay enabled: part of the force of `initialize_then_mint_uses_stored_admin` comes from the path after `mint` being reachable (a wrong key/durability would make `mint`'s `.unwrap()` trap and the trailing asserts hold vacuously). That half is additionally stated positively by the `cvlr_assert!(admin_opt(&e) == Some(a))` placed between the two calls.
* `cvlr_soroban::Addr` could not be used for logging: `cvlr` (git) and `cvlr-soroban` 0.4.0 resolve different `cvlr-log` crates, so `Addr`'s `CvlrLog` impl is for a different trait than `clog!` requires (E0277). Addresses are logged as raw payloads via `addr_id`.

Verdicts (final prover run):
* VERIFIED — `initialize_persists_admin`, `initialize_then_mint_uses_stored_admin`. Property 4 holds: `initialize(a)` from an uninitialized state stores exactly `a` under the key and durability `mint` reads, and the subsequent `mint` succeeds, requires `a`'s authorization, and credits the recipient by exactly `amount`.
* VIOLATED, declared expected failures — `unauthenticated_admin_overwrite_enables_unlimited_mint`, `initialize_is_one_shot`, `admin_rotation_requires_current_admin_auth`. These are three views of one real defect: `Token::initialize` is a bare `e.storage().persistent().set(&"ADMIN", &admin)` with no `require_auth` on anyone (neither the incumbent nor the incoming admin) and no `has(&"ADMIN")` re-initialization guard. The counterexamples show `initialize`'s frame containing only the key conversion and `put_contract_data` — no auth host call — the stored admin replaced by an arbitrary caller's address, and then `mint` authorizing against the attacker and inflating the recipient's balance while the standing admin authorized nothing.

Remediation the findings call for (no tool edits the contract): add a one-shot guard (`if has(&"ADMIN") { panic!() }`) and `admin.require_auth()` to `initialize`, and, if rotation is wanted at all, move it to a separate `set_admin` that reads the incumbent and requires *its* authorization before overwriting — the pattern `mint` already uses correctly.
